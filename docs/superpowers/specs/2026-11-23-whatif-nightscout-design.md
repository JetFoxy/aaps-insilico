# What-if на своих данных из Nightscout — проектная записка

Дата: 2026-11-23
Статус: на согласовании, код не начат
Основание: запрос владельца («подать свою статистику из Nightscout и увидеть, как меняются
настройки алгоритмов»), разбор `ga-zelle/APS-what-if`, текущий стенд `aaps-insilico`

## 1. Зачем

Дать человеку прогнать **свой** день из Nightscout через настоящий Kotlin-код AAPS и увидеть,
что изменится, если поменять коэффициенты autoISF или выбрать другой алгоритм (autoISF / DynISF /
SMB выключен). Не «средний пациент из статьи», а собственный трейс: свои углеводы, свои болюсы,
свой профиль.

Два разных вопроса, и их нельзя смешивать:

| Вопрос | Режим | Что меняется | Чего не показывает |
|---|---|---|---|
| «Что алгоритм сделал бы иначе?» | `replay` | инсулин, SMB, базал, IOB, решения | глюкозу и TBR — они остаются вашими |
| «Что было бы с глюкозой?» | `model` | глюкоза, TBR, TIR, инсулин | точность: это модель, а не ваш день |

APS-what-if отвечает только на первый вопрос: он подменяет настройки, но глюкозу берёт из лога.
Поэтому его колонка «TBR» на деле показывает базал, а не время в гипогликемии. Мы делаем оба
режима и подписываем, что именно видно на графике.

**Не цель:** клинические выводы, советы по настройке помпы, «одобренный» прогноз.
**Анти-цели:**

- модель выдаётся за реальный день (и наоборот);
- в replay показывается «TBR после смены настроек» — это математически невозможно, глюкоза та же;
- токен Nightscout попадает в лог, кэш, git или URL наших страниц;
- виртуальный пациент подбирается молча, без отчёта о том, насколько он похож.

## 3. Вход: Nightscout по ссылке с токеном

### 3.1 Запросы

Только чтение, только с локального сервера (браузер не видит токен):

| Данные | Запрос |
|---|---|
| CGM | `GET /api/v1/entries.json?count=20000&find[type]=sgv&find[date][$gte]=<epoch_ms>` |
| Лечение | `GET /api/v1/treatments.json?count=5000&find[created_at][$gte]=<ISO8601>` |
| Профиль | `GET /api/v1/profile.json` |
| Статус помпы | `GET /api/v1/devicestatus.json?count=5000&find[created_at][$gte]=<ISO8601>` |

Авторизация: `?token=<access token>`; если инстанс не принимает — заголовок `api-secret`
(sha1-хэш секрета). Оба варианта пробуются по очереди, ошибка 401 показывается человеку
без эха токена.

`devicestatus` обязателен для W2: в `openaps.suggested` лежит полная запись решения
(`insulinReq`, `finalIsf`, факторы `autoIsf`, `smbOn`, `rate`, `eventualBG`, `predBGs`,
`sensitivityRatio`, `deliverAt`). Это эталон, с которым сверяется replay.

### 3.2 Нормализация (`python/nightscout/trace.py`)

`DayTrace`:

- `entries: list[CgmPoint]` — `ts` (epoch ms), `mgdl`, `direction`, `device`; только `type == "sgv"`,
  калибровки и `mbg` отбрасываются; дубли по `ts` схлопываются (последний выигрывает).
- `treatments: list[Treatment]` — `ts`, `kind` (`bolus` | `carbs` | `temp_basal` | `temp_target` |
  `profile_switch` | `note`), `amount`, `duration_min`, `origin` (`manual` | `loop` | `pump`).
  В Nightscout 15, на котором проверено, SMB помечается полем `type == "SMB"`, обычный болюс —
  `type == "NORMAL"`; `isSMB`/`automatic` отсутствуют. Temp basal: `absolute` (ед/ч) + `duration`;
  длительности короткие (2–9 мин), поэтому семантика «остаток/минуты хода» обязательна.
  Temp target: `targetBottom`/`targetTop` + `duration` + `reason` (`Automation` — типичный).
  Profile switch: `profileJson` — **строка** JSON с полным профилем и `iCfg`.
- `profile: ProfileSnapshot` — `basal`, `sens`, `carbratio`, `target_low/high` по времени суток,
  `units`, `timezone`; `dia` в проверенном профиле отсутствует, поэтому DIA берётся из `ICfg`
  экспорта настроек.
- `devicestatus: list[DecisionRecord]` — `ts`, `deliverAt`, `insulinReq`, `finalIsf`, факторы
  `autoIsf` (`acceIsf`, `bgIsf`, `ppIsf`, `duraIsf`, `iobThEffective`, `smbOn`, `smbOffReason`),
  `rate`, `eventualBG`, `predBGs`, `sensitivityRatio`, `iob`. Записи приходят чаще циклов,
  поэтому дубли схлопываются по `deliverAt`.
- `window_start`, `window_end`, `timezone`, `sensor`, `source_host_hash`.

Инварианты:

- всё в epoch ms, поэтому переход на летнее время не ломает шаг;
- сенсорный вход — сырые отметки; в проверенном трейсе шаг 1 мин (p95 — 3 мин), поэтому
  пересэмплирование запрещено: оно бы подменило дельты и работу UKF;
- решения — на 5-минутной сетке, привязанной к первой точке окна;
- пропуски CGM > 15 мин не заполняются: replay их пропускает и помечает в отчёте;
- профиль в mmol/L переводится в mg/dL (`× 18.0`), единицы фиксируются в отчёте.

### 3.3 Хранение и приватность

- **В v1 кэша на диске нет.** Импорт живёт в памяти процесса, рестарт его не воскрешает.
  Это убирает «трейс лежит на диске, а UI про него не знает».
- Токен живёт в памяти процесса на время импорта; в логах и ошибках вырезается (`token=***`).
- Сервер слушает `127.0.0.1` по умолчанию; в Docker — тот же bind, порт публикуется на localhost.
- Кнопка «удалить импорт» чистит память.
- `data/nightscout/` остаётся в `.gitignore` на случай будущего кэша и ручных выгрузок.

### 3.4 Настройки AAPS — обязательный второй вход

Nightscout отдаёт профиль (базал, ISF, CR, цели, единицы, часовой пояс) и его историю: 15 профилей
в `store`, активный на `startDate`, плюс `Profile Switch` с полным `profileJson`. Этого достаточно
для профиля — **экспорт настроек для профиля не нужен**.

Чего в Nightscout нет (и это определяет решения алгоритма):

- веса autoISF (`bgAccel_ISF_weight`, `bgBrake_ISF_weight`, `pp_ISF_weight`, `dura_ISF_weight`,
  `autoISF_min/max`, `dynisf_*`);
- `max_iob`, `max_basal`, `SMBInterval`, `bolus_increment`, флаги SMB;
- `ApsAutoIsfSmbDeliveryRatio` и её min/max/диапазон по BG;
- `ICfg` — пик и длительность действия инсулина (`insulin_configuration`). Он встречается в
  `profileJson` при переключениях профиля, но не на каждом цикле, поэтому основным источником
  остаётся экспорт.

Без них baseline-прогон не может совпасть с реальными решениями, то есть W2 недостижим в принципе.
Поэтому импорт настроек — не «приятное дополнение», а предусловие replay:

1. UI просит экспорт настроек AAPS (Settings → Maintenance → Export settings).
2. AAPS пишет его **зашифрованным** (`"format": "aaps_encrypted"`): base64
   `[1 байт длины IV][IV][шифротекст + тег]`, ключ — PBKDF2-HMAC-SHA1, 50 000 раундов, соль из
   `security.salt`, шифр AES-GCM с 128-битным тегом. Разбор — в `python/nightscout/prefs.py`.
   Зависимость — `cryptography` (её нет в текущем `requirements.txt`).
3. Пароль спрашивается в UI на один импорт, в памяти, никогда не пишется на диск и в лог.
   Если экспорт без шифрования (`"algorithm": "none"`), пароль не нужен.
4. Файл разбирается тем же `load_prefs`/`insulin_from_settings`, что и стенд; токен и трейс к нему
   не прикасаются.
5. Если настройки не загружены — replay **не запускается**; model-режим запускается, но с плашкой
   «настройки стенда, не ваши».
6. `ICfg` из экспорта главнее `dia` из профиля Nightscout: IOB считает мост по `ICfg`.
   В проверенном профиле `dia` вообще нет, так что это единственный источник.

## 3.5 Что берём из реального дня, а что игнорируем

| Событие | v1 | Почему |
|---|---|---|
| болюсы, углеводы | берём | это вход |
| temp basal (treatments) | берём, включая короткие 2–9 мин | иначе IOB и реальный базал врут |
| temp target | **реконструируем** из `Temporary Target` | в проверенных данных 136 TT за 3 дня, 115 — из автоматизации; без них сверка бессмысленна |
| autosens / ratio | берём `sensitivityRatio` из `devicestatus` | он записан на каждом цикле |
| exercise mode | выключен, предупреждение | нет надёжного признака в NS |
| profile switch | применяем на его времени, профиль из `profileJson` | 5 переключений за 3 дня |

W2-приёмка допускает TT и profile switch (они воспроизводятся). Если встретился exercise или
неизвестное событие — replay работает, но в отчёте стоит «не воспроизведено: …».

## 4. Режим `replay` — что алгоритм сделал бы иначе

### 4.1 Ход прогона (`python/runner/replay_loop.py`)

1. `init` моста: профиль из Nightscout, настройки и `ICfg` из экспорта AAPS, история лечения за 8 ч
   до `window_start` (болюсы, углеводы, temp basal) — чтобы IOB на старте был честным.
2. Точки решения — 5-минутная сетка, привязанная к первой точке окна. Сенсорный вход — **сырые**
   отметки Nightscout без пересэмплирования: UKF и дельты в мосте зависят от реального шага.
   Если сенсор пишет чаще 5 мин, в окно попадают все точки, а решение принимается на сетке.
3. На каждую точку решения:
   - `glucose` — реальное показание и окно истории для UKF/дельт;
   - `cycle` — настоящий алгоритм с настройками варианта; на этот цикл подаются активный
     temp target, `sensitivityRatio` из `devicestatus`, активный профиль (после `profile_switch`)
     и `currentTemp` с остатком/минутами хода для коротких temp basal;
   - решение (temp basal, SMB, болюс) пишется в **свой** журнал варианта.
4. Глюкоза **не пересчитывается**: следующим шагом снова подаётся реальное показание.
   Поэтому варианты различаются только доставленным инсулином и решениями.

Инсулин варианта учитывается в его собственном IOB (мост получает решения варианта как
treatments), но не влияет на сенсор. Это и есть «counterfactual decisions»: видно, что алгоритм
сделал бы, но не утверждается, что глюкоза осталась бы той же.

**Пропуски CGM.** Если между точками больше 15 мин, цикл пропускается: SMB не выдаётся, а
последний temp basal продолжает начисляться в IOB варианта (иначе IOB занижен до конца окна).
Доля пропущенных циклов выводится в отчёте.

### 4.2 Болюсы и классификация лечения

В проверенном Nightscout 15 SMB помечается `type == "SMB"`, обычный болюс — `type == "NORMAL"`;
полей `isSMB`/`automatic` нет. `enteredBy` заполнен меньше чем у трети записей, поэтому опираться
на него нельзя.

- `real-boluses` (по умолчанию) — болюсы `type == "NORMAL"` остаются; `type == "SMB"` из входа
  **удаляются**: это выход алгоритма, а не действие человека. Иначе вариант добавит свои SMB
  поверх реальных и IOB удвоится. Число исключённых болюсов выводится в отчёте.
- `algorithm-only` — все болюсы исключены; алгоритм ведёт еду по объявленным углеводам.
  Если углеводы не объявлены, еда считается необъявленной.
- Записи без `type` (в проверенных данных их 310 из 577 болюсов) считаются ручными, если у них
  есть `carbs` или `notes`; иначе — в «неклассифицировано» и в отчёт. Молча угадывать нельзя.

### 4.3 Что показываем

- график инсулина: реальный (из treatments + devicestatus) против варианта, по циклам;
- SMB: количество и сумма, temp basal: суммарные единицы и время на 0;
- IOB варианта против реального IOB;
- решения: `insulinReq`, `finalISF`, факторы (acce/bg/pp/dura), `ratio`, причина;
- **глюкоза — одна реальная линия для всех вариантов**, подписана «ваш CGM, не прогноз»;
- метрики: суммарный инсулин, SMB, базал, средний IOB, число отказов/пауз.
  TIR/TBR в replay **не считаются** — они по построению одинаковы; вместо них честная плашка.

### 4.4 Проверка честности replay

Baseline-прогон использует **ваши** настройки из экспорта AAPS (веса autoISF, `max_iob`,
`max_basal`, `SMBInterval`, `bolus_increment`, `ApsAutoIsfSmbDeliveryRatio`, `ICfg`) и профиль из
Nightscout. Если экспорта нет — проверка не запускается.

Эталон — не «примерно», а `openaps.suggested` из `devicestatus`: на каждом цикле там записаны
`insulinReq`, `finalIsf`, `acceIsf`/`bgIsf`/`ppIsf`/`duraIsf`, `smbOn`, `rate`, `sensitivityRatio`.
Сверяем построчно, допуски фиксируем **до** первого прогона:

| Поле | Допуск |
|---|---|
| `finalIsf`, `acceIsf`, `bgIsf`, `ppIsf`, `duraIsf` | ±0.01 |
| `insulinReq` | ±0.05 ед |
| `rate` (temp basal) | ±0.05 ед/ч |
| `smbOn` | точное совпадение |
| число циклов | ≥ 95 % циклов сопоставимы по `deliverAt` (±1 мин) |

Циклы, где входные данные не восстановимы (пропуск CGM, exercise, неизвестное событие), из
процента исключаются и перечисляются в отчёте. Если сходимость ниже — сначала чинится replay,
и только потом строятся варианты.

### 4.5 SMB-доля

В replay никакого пересчёта по каденции нет: `ApsAutoIsfSmbDeliveryRatio` берётся из экспорта
настроек как есть и применяется на 5-минутном цикле, как в AAPS. Стендовый коэффициент
`cadence/3` (`smb_ratio_for_cadence`) — конвенция harness'а для 1-минутных прогонов, в replay он
не используется.

### 4.6 Отчёт о похожести и пропусках

Каждый прогон заканчивается блоком «что не воспроизведено»: temp target, autosens-отклонения,
exercise, смена профиля, пропуски CGM > 15 мин, исключённые SMB-болюсы. Без этого блока результат
не считается принятым.

## 5. Режим `model` — что было бы с глюкозой

### 5.1 Подбор физиологии

Модель не знает вашего веса и кинетики, поэтому:

1. Из профиля считаются TDI (сумма базала × 24 + средние болюсы), CR, ISF.
2. Ищется ближайший субъект когорты по `log(TDI)`, `log(CR)`, `log(ISF)` (евклидово расстояние
   в лог-пространстве, веса 1:1:1).
3. В отчёт выводятся: выбранный субъект, расстояние, его BW, TDI, CR, ISF и ваши значения.
   Если расстояние выше порога — плашка «похожесть низкая, результат — иллюстрация».
4. Ручная правка: BW и TDI можно задать вручную; профиль алгоритма (sens/CR/target/basal)
   всегда ваш, из Nightscout.

### 5.2 Прогон

- Еда — ваши записи `carbs`; болюсы — по переключателю из §4.2.
- **Начальное состояние** собирается общим с replay «seed history»: история лечения за 8 ч до
  `window_start` заполняет компартменты инсулина (IOB), углеводов (COB) и глюкозы, затем начальная
  глюкоза подгоняется под вашу в `window_start`. Без этого окно, начатое через час после болюса,
  моделировалось бы как «чистый» пациент и TIR был бы фикцией.
- Сенсор: по умолчанию без шума (детерминированно); шум можно включить и зафиксировать seed.
- Длительность — окно импорта.
- Выход: модельная глюкоза, IOB/COB, инсулин; TIR/TBR/LBGI против вашего реального дня
  как референса.

## 6. Варианты и сравнение

Вариант = `{алгоритм: off | autoisf | dynisf, smb: on | off, веса autoISF, правки профиля,
метка, цвет}`.

- `off` — autoISF выключен, обычный OpenAPS SMB работает (как плечо `off` в стенде).
- `smb: off` — отдельный вариант: `microBolusAllowed = false`, базал и болюсы считаются.
- До 4 вариантов + базовый («как в реальности» для replay, «профиль как есть» для model).
- Варианты считаются последовательно на одном импортированном трейсе.
- UI: чипы вариантов, «копировать», «сбросить к профилю», сравнение «как было / как стало».
- Детерминизм: одинаковый трейс + настройки + seed → одинаковые числа (тест).


`requirements.txt` получает `cryptography`; образ Docker пересобирается.

Эндпоинты:

- `POST /api/whatif/import` `{url, token, days, prefs_file?}` → `{trace_id, summary}`;
  `prefs_file` — содержимое экспорта настроек AAPS (обязателен для replay);
- `GET  /api/whatif/trace/<id>` → сводка (диапазон, число точек, углеводы, болюсы, профиль,
  предупреждения о пропусках и невоспроизведённых событиях);
- `POST /api/whatif/run` `{trace_id, mode, variants, options}` → `{run_id}`;
- `GET  /api/whatif/stream?id=<run_id>` → SSE: `start`, `variant`, `cycle`, `done`, `error`;
- `DELETE /api/whatif/trace/<id>` → удалить импорт.

Ошибки: `400` — плохие параметры, `401` — Nightscout не пустил, `502` — Nightscout недоступен,
`409` — окно без данных CGM.

## 8. Ограничения и режимы отказа

| Ситуация | Поведение |
|---|---|
| нет `devicestatus` | replay работает, но W2-сверка невозможна — плашка «нет эталона решений» |
| нет экспорта настроек AAPS | replay не запускается; model — с плашкой «настройки стенда» |
| экспорт зашифрован, пароль неверен | 400 «не удалось расшифровать», файл и пароль не сохраняются |
| пропуски CGM > 15 мин | цикл пропускается, temp basal продолжает начисляться, в отчёте доля пропусков |
| нет профиля в Nightscout | импорт останавливается: без ISF/CR/базала сравнивать нечего |
| смена профиля внутри окна | применяем `profile_switch` на его времени |
| короткие temp basal (2–9 мин) | считаем по `duration` и остатку, не округляем до 30 мин |
| часовой пояс/DST | всё в epoch ms; профиль по времени суток — в своей зоне |
| токен только на запись | 401 с понятным текстом, без повторов |
| больше 14 дней | предупреждение о времени прогона, окно режется до 14 дней по умолчанию |

## 9. Приватность (жёсткие правила)

- Токен и URL не пишутся в логи, кэш, git, скриншоты и отчёты.
- В документации и тестах — только плейсхолдеры (`<ns-url>`, `<token>`), синтетические фикстуры.
- `data/nightscout/` в `.gitignore`; проверка в CI-скрипте репозитория на случай случайного коммита.
- Скриншоты для README делаются на синтетическом трейсе.
- Импорт живёт только в памяти процесса; на диск не пишется; рестарт его не воскрешает.
- Экспорт настроек AAPS содержит `ICfg` и веса, но не содержит трейс; он тоже не пишется на диск.

## 10. Этапы

| Этап | Что | Приёмка |
|---|---|---|
| W1 | клиент Nightscout + нормализация + расшифровка экспорта настроек + сводка | синтетический мок-сервер; тест «токен не в логе»; тест расшифровки на синтетическом файле; импорт 3 дней |
| W2 | replay-движок + сверка с `openaps.suggested` | допуски §4.4 зафиксированы до прогона; отчёт по каждому полю |
| W3 | model-движок + подбор субъекта + seed history | отчёт о похожести; детерминизм по seed |
| W4 | UI + SSE + i18n + Docker | ручной чек-лист, скриншот на синтетике |

## 11. Решения исполнителя (можно оспорить)

1. Два режима, а не один: replay честно показывает решения, model — глюкозу.
2. Болюсы по умолчанию остаются реальными: сравнение настроек, а не стратегии еды.
3. В replay не считаем TIR/TBR — иначе получится ложь.
4. Подбор субъекта — ближайший сосед по (TDI, CR, ISF) с отчётом расстояния, без подгонки.
5. Токен только на сервере, только в памяти.
6. Окно по умолчанию — 3 дня; максимум 14.
7. Экспорт настроек AAPS — обязателен для replay; расшифровка локальная, пароль не хранится.
8. Temp target и profile switch воспроизводятся; autosens берётся из `devicestatus`;
   exercise в v1 не воспроизводится и попадает в отчёт.
9. Сенсорный вход — сырые отметки NS (в проверенных данных шаг 1 мин); решения — на 5-минутной сетке.
10. SMB определяется по `type == "SMB"`; такие болюсы исключаются из входа в обоих подрежимах.
11. `off` = autoISF выключен, SMB включён; `smb: off` — отдельный вариант.
12. SMB-доля в replay — из настроек как есть, без пересчёта по каденции.
13. W2 сверяется с `openaps.suggested` по полям, допуски зафиксированы в §4.4.

## 12. Что осталось решить владельцу

Открытых вопросов по устройству нет. Осталось подтверждение: начинаем с W1–W2 (импорт + replay
с коэффициентами), затем W3 (model и сравнение алгоритмов), затем UI. Если хотите другой порядок —
скажите сейчас.
