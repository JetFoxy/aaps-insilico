# Стенд in silico для AAPS + autoISF — проектная записка

Дата: 2026-11-10
Статус: на согласовании, код не начат
Основание: `docs/PLAN.md` (рабочее задание), решения ниже

## 1. Зачем

Реальный код autoISF должен работать в замкнутом контуре с виртуальным пациентом, чтобы
сравнивать варианты алгоритма при одинаковых сценариях: еда, физическая нагрузка, шум и лаг
CGM, ошибки профиля, тип инсулина.

**Не цель:** клинические выводы, воспроизведение FDA-принятой популяции, советы пользователям.
Модель называть «UVA/Padova-подобная по Visentin et al. 2018», не «UVA/Padova simulator».

**Анти-цели** — то, что сделает затею провальной даже при работающем коде:

- стенд прав только потому, что мы подогнали параметры под ожидаемый результат;
- алгоритм в стенде — порт на Python, а не настоящий код AAPS;
- версия алгоритма в отчёте не зафиксирована;
- результат преподнесён как основание для клинических решений.

## 2. Решения

| Решение | Кто | Обоснование |
|---|---|---|
| Ядро физиологии — Python (`numpy`/`scipy`), мост — JVM | исполнитель | ядро меняется часто, алгоритм — никогда |
| Алгоритм вызывается как настоящий Kotlin-код, не портируется | исполнитель + согласовано | порт дрейфует от исходника, а сравнение вариантов без исходника бессмысленно |
| Пин алгоритма: `autoisf-3.2.1` @ `2d08884674` | владелец | 4.0-apex-integration подтянем, когда автор обновит код под 4.x |
| IOB/COB не портируем, а считаем тем же JVM-кодом AAPS | исполнитель | расхождение по IOB — самый тихий способ разойтись с приложением |
| W1 (мост на реальных данных) идёт до физиологической модели | владелец | он либо подтверждает честность моста, либо ломает затею на первой неделе |
| Репозиторий локальный, без remote | исполнитель, требует подтверждения | публичность и лицензия не решены |
| CGM-шум берём из реальных остатков, а не генерируем «похожий» | исполнитель | в `docs/PLAN.md` §1 параметры шума S2017 недоступны |

## 4. Архитектура

Один цикл — 5 минут. Python ведёт физиологию и историю, JVM отвечает за всё, что является
кодом AAPS.

```
        ┌──────────────── Python ────────────────┐
        │ физиология (S2017) │ нагрузка │ CGM │ помпа │
        └───────────────┬────────────────────────┘
                        │ JSON-строка: полное состояние цикла
        ┌───────────────▼────────────────────────┐
        │ JVM-мост: adapter выбранной цели       │
        │ (autoISF / DynamicISF / Boost / AIMI)  │
        │  determine_basal + iobCalc + (COB)     │
        └───────────────┬────────────────────────┘
                        │ JSON-строка: RT (rate, duration, insulinReq, smb, факторы, console)
```

**Границы.** Python не содержит ни одной строки алгоритма и ни одной строки расчёта IOB.
JVM не содержит ни одной строки физиологии.

**Контракт моста** (`bridge/`, JSON-строки, один долгоживущий процесс):

| Команда | Вход | Выход |
|---|---|---|
| `init` | профиль, настройки autoISF (все ключи `preferences`), тип инсулина | `ok` |
| `step` | glucose_status, currenttemp, iob_array, meal_data, autosens, флаги, время | `RT` + `consoleLog`/`consoleError` |
| `iob` | история доз и temp basal, время | массив `IobTotal` |
| `selftest` | — | прогон встроенного фикстура, сверка с эталоном |

Запуск: classpath `androidHostTest` резолвится одним вызовом Gradle на старте, дальше
`java -cp ... app.aaps.sim.SimBridge` без Gradle. В каталоге плагина нет ни одного
`import android`, Robolectric не нужен; `determine_basal` принимает только data-объекты
(`DetermineBasalAutoISF.kt:214-218`).

**Каденс цикла — сценарий, 1–5 минут.** Внешний цикл (как часто вызывается алгоритм, обновляется
CGM и помпа) задаётся сценарием: 1, 2, 3, 4, 5 мин. Внутри `determine_basal` всё привязано к
5-минутной сетке жёстко: горизонт предсказания 48 блоков по 5 мин, `dev` считается как
`30/5 * delta`, `fiveMinBlocks = 24` (`DetermineBasalAutoISF.kt:75-76, 404-410, 665-669`). Поэтому
контракт фиксирует единицы, а не каденс:

- дельты глюкозы в `glucose_status` всегда нормированы на 5 минут, независимо от каденса;
- массив IOB — 48 точек с шагом 5 мин;
- при каденсе 1 мин алгоритм вызывается в 5 раз чаще, и упор делает `SmbIntervalGate`
  (интервал SMB задаётся в минутах, а не в шагах) — это и есть измеряемый эффект.

Смысл оси — не точность предсказания, а **частота решений**: число SMB в сутки, коррекции в
падающую глюкозу, суммарная доза. По `tools/loop-sim/` именно эта ось чувствительна (σ=3 мг/дл
даёт +42 % SMB без потери TIR), а по TIR/TBR каденс почти не виден.

### 4.1 Целевые алгоритмы (targets)

Стенд не про один autoISF. Каждый алгоритм — отдельная цель: зафиксированный коммит, свой
adapter, своя сборка. Общий у них только JSON-контракт (`schema/v1`), внутри — настоящий код
этого форка, включая его собственные IOB/COB.

| Target | Где | Состояние |
|---|---|---|
| `autoisf@<сборка из данных>` | `autoisf`-форк AAPS | рабочий, золотые данные 17 904 цикла |
| `autoisf@2d08884` | `autoisf-3.2.1` | текущий целевой, замеряет дрейф от предыдущего |
| `dynamicisf` | `4.0-apex-integration`, `DetermineBasalSMB` + `runningDynamicIsf` | золотые данные 602 цикла |
| `boost` | `~/Projects/Dia/Boost-in-AAPS_3.4`, `DetermineBasalBoost`/`V2`/`V3`/`AMA` | adapter нужен, золотых данных нет, есть свои тесты |
| `aimi` | `~/Projects/Dia/OpenApsAIMI` | только через ONNX-путь: tflite требует Android, а ONNX-модели в репозитории — заглушки (`scripts/generate_oref_stub_onnx.py` прямо это пишет) |

Почему IOB/COB берём у самой цели: у Boost и AIMI своя математика IOB/COB, и общий расчёт
сделал бы сравнение алгоритмов сравнением двух разных IOB. Это тот самый случай, когда
«не портировать» окупается второй раз.

Приёмка расширяемости: один и тот же сценарий прогоняется на всех собранных целях, adapter
падает громко при несовпадении схемы, и добавление цели не трогает `python/`.

### 4.2 Режим еды: оба режима, равноправно

Стенд гоняет каждый сценарий в двух режимах, и оба равноправны — сравнивать алгоритмы
только в одном нельзя, иначе половина их поведения не проверена.

| Режим | Что видит физиология | Что видит алгоритм |
|---|---|---|
| **FCL, еда не объявлена** | приём пищи по модели S2017 | `carbs = 0`, `mealCOB = 0`, время еды не задано |
| **Объявленная еда** | тот же приём | `carbs`, `mealCOB`, время последнего углевода |

В FCL COB не считается — считать нечего, и «помочь» алгоритму оценкой COB значит тестировать
другой продукт. COB как компонент стенда существует только во втором режиме, где он
действительно является входом. IOB в обоих режимах в порядке: инсулин помпа записывает всегда.

Третий вариант, который стоит держать в матрице (моё предложение): **объявлено, но болус не
введён**. В жизни это обычное дело — углеводы записаны, болюс забыт, — и он отделяет вклад
объявления от вклада болюса: в объявленном режиме с болусом сравниваются алгоритмы, в
объявленном без болюса — их реакция на известную, но не покрытую еду.

Золотые данные это подтверждают: из 9 247 наблюдений COB значение 0 в 7 764, при этом за
4 недели всего 360 записей углеводов (8 800 г) и 2 810 записей инсулина. Оба режима в реплее
есть, досочинять ничего не надо.

Метрики делятся на общие (TIR, TBR <70 и <54, LBGI, число SMB, суточная доза) и режимные:
для FCL — постпрандиальный пик и время выше 180 без объявления; для объявленной еды — вклад
болюса, промах по пику, коррекции после еды.

**Харнесс живёт в нашем репо**, а не в AAPS: `bridge/src/` копируется в
`plugins/aps/src/androidHostTest/kotlin/app/aaps/sim/` во временном worktree на пине,
сборка — скриптом, в AAPS ничего не коммитится.

## 5. W1 — скелет на реальных данных

Цель: доказать, что мост воспроизводит решения настоящего приложения на его же входных данных.

**Данные.** 4 выгрузки Nightscout devicestatus (окт 2026), 26 897 записей, 4 недели:

- autoISF: 17 904 записи в suggested/enacted, из них 3 799 enacted — есть `rate`, `duration`, `smb`;
- DynamicISF: 602 записи `algorithm = SMB` с `runningDynamicIsf` — второй target проверяется
  тем же прогоном, а не отдельным проектом;
- чистый FCL: 11 046 циклов AUTO_ISF с `COB = 0` во всех и нулём записей углеводов, на двух
  отрезках — 1–14.10 (CGM 1 мин) и 1–10.11 (CGM 5 мин); 15–31.10 выгрузки CGM нет, эти циклы
  переиграть нечем.

Дубли в выгрузках обязательны к дедупликации: 1 585 пар devicestatus с нулевым интервалом по
`suggested.timestamp`, и на первом сайте 7 992 пары записей CGM ближе 60 с.

**Восстановление входов** (что откуда):

| Поле `determine_basal` | Источник |
|---|---|
| `glucose_status` | не из `bg` цикла: реплей сырого CGM через настоящие `UnscentedKalmanFilterPlugin` → `AutosensDataStoreObject.createBucketedData` → `GlucoseStatusCalculatorAutoIsf` (см. 5.1) |
| `iob_data_array` | `iobCalc` моста по истории доз и temp basal из treatments |
| `meal_data` | `COB` цикла, `carbs` и время еды из treatments |
| `profile` | ISF/CR/Target печатаются в `reason` каждого цикла; остальное — из профиля на дату |
| `autosens_data` | `sensitivityRatio` цикла |
| `currenttemp` | `enacted` предыдущего цикла |
| флаги (`microBolusAllowed`, `autoIsfMode`, ...) | `runningAutoIsf`, `pump.extended`, настройки |
| настройки autoISF и SMB | экспорт настроек AAPS (`tools/decrypt_prefs.py`); снимок на дату экспорта, а не на октябрь — расхождение учитывается при разборе несовпадений |

**Сравнение:** `rate`, `duration`, `smb`, `insulinReq`, `eventualBG`, векторы `predBGs`, строка
факторов. Каждое расхождение сохраняется в отчёт с полным входом цикла.

### 5.1 `glucose_status` восстанавливается только полным конвейером

Проверено на золотом наборе: `glucose_status` нельзя собрать из `bg` цикла и соседних `bg`.

- Сенсор — Libre 2 через xDrip (`iGlucco`/`Libre2`, шаг ≈3 мин), а `LIBRE_2`
  входит в `ADVANCED_FILTERING_SENSORS`. Поэтому в `GlucoseStatusCalculatorAutoIsf`
  срабатывает `useRawFit`: парабола и `duraISFminutes` считаются по **сырым** 3-минутным
  отсчётам с `scaleTime = scaleBg = 1`. Это восстановимо из `entries` один в один.
- А `glucose`, `delta`, `shortAvgDelta`, `longAvgDelta` берутся из `bucketedData`, к которому
  `PrepareGraphDataRunner.smoothData()` уже применил `UnscentedKalmanFilterPlugin` и калибровку.
  Сглаженных значений в Nightscout нет: `bg` цикла — это `smoothed`-значение на 5-минутной
  сетке, а не сырой `sgv` (медиана расхождения 0.9 мг/дл, p99 — 9.1). Калибровок в октябре не
  было (`eventType = Calibration` отсутствует), поэтому `calibrated = null`, но UKF обязателен.
- Состояние UKF в экспорт не входит: `ukf_last_processed_timestamp` помечен
  `exportable = false`, экспортируется только текущее `ukf_learned_r`. Сброс обучения
  привязан к событиям `Sensor Change` (в октябре их два), и его можно воспроизвести.

Отсюда W1 гоняет тот же конвейер, а не приближение:

```
entries (сырой CGM)
  → AutosensDataStoreObject.loadBgData       (окно 34 ч, как у приложения)
  → createBucketedData                       (сетка 5 мин, referenceTime живёт между циклами)
  → UnscentedKalmanFilterPlugin.smooth       (bucketedData) + smoothWithoutLearning (statusData)
  → GlucoseStatusCalculatorAutoIsf           (useRawFit по сырому ряду)
  → DetermineBasalAutoISF.determine_basal
```

Приёмка по входу, до всякого `determine_basal`: переигранный `glucose` должен совпасть с
записанным `bg` цикла, а переигранные `acceleration`/`correlation`/`parabolaMinutes` — с
записанными в `consoleError` (`Parabola fit results were ...`). Если это не сходится, дальше
идти нельзя: расхождение в `RT` уже не будет виной алгоритма.

Остаётся один честно неизвестный вход — стартовое `learnedR` на 1 октября. Он адаптивный и
ограничен `[16, 225]`; по умолчанию берём `rInit = 25.0` и в отчёте отдельно показываем
чувствительность к этому старту.

### 5.2 Первые результаты W1 и что они изменили в постановке

Собрано и проверено на реальных данных (`4.0-apex-integration@74271a544b`, мост `sim-bridge`
на JVM, без Android):

| Проверка | Результат |
|---|---|
| `glucose` после UKF+бакетирования против записанного `bg` | 237/250 точно, p99 = 1.8 мг/дл |
| `bgAcceleration` против `Parabola fit results` | медиана 0.003, p90 = 0.005, p99 = 1.84 |
| `corrSqu` / `parabolaMinutes` | p90 = 0 и 0.0 |
| `IOB[0]` против `suggested.IOB` | медиана 0.007 ЕД, p90 = 0.013, p99 = 0.022 |
| `autoISF()` против записанного `sens:` | 18/30 в пределах 0.1 ЕД/мг-дл; хвост — из-за `duraISFminutes` |
| полный `step` (250 циклов, COB = 0, чистый интервал) | `rate` 192/250, `duration` 234/250, `smb` 243/250 |
| `insulinReq` на том же прогоне | медиана 0.00, p90 = 0.02, p99 = 0.12 |
| `eventualBG` | медиана 1.0, p90 = 5, p99 = 30 |

Три вывода, которые меняют постановку:

1. **Золотой набор нельзя переигрывать одним коммитом.** Владелец обновлял сборку почти каждый
   день: `74271a5` (Oct 6–8) — 732 цикла, `a199b37` (Oct 15–22) — 3 017, `b2cce90` (Oct 2–6) —
   1 649, и ещё десять сборок. Каждая сборка — отдельный target и отдельный прогон; сравнивать
   циклы Oct 20 с кодом Oct 6 бессмысленно.
2. **CGM в Nightscout писали несколько приложений.** Oct 1–4 параллельно лился `iGlucco`
   (≈1 мин, 7 555 точек) — это не тот поток, что получал AAPS. С Oct 7 19:04 UTC сменился
   и xDrip-аплоадер (`Libre2` → `xDrip-LibreReceiver Libre2 Native`), причём поток стал ~6-мин.
   Поэтому чистый интервал для `74271a5` — **Oct 6 18:00 – Oct 7 19:04 UTC**, на нём и получены
   числа выше. Остальное требует отдельного разбора источника, а не «ещё один прогон».
3. **Поздние сборки: CGM закрыт базой xDrip, остались slopes.** После Oct 7 19:04 UTC
   Nightscout отдаёт не тот поток (2/80 точных `glucose`). В базе xDrip он есть: колонка
   `BgReadings.raw_data` (316 739 отсчётов) даёт 240/250 точных `glucose` и p90 `bgAcceleration`
   0.005 на `a199b37`. `MealData.slopeFromMaxDeviation`/`slopeFromMinDeviation` и `mealCOB`
   считаются oref1-пайплайном COB; он подключён настоящим кодом (`meal`-команда моста вызывает
   `PrepareGraphDataRunner.runIobCobOref1`). COB сходится с записанным в пределах 0.2–0.7 г,
   а `UAM Impact` — медиана 0.10, p90 0.40 мг/дл/5м: slopes и углеводный вход верны.
4. **`useRawFit` определяется настройками, а не сенсором.** На чистом интервале приложение
   считало параболу по сырым 3-минутным отсчётам (`useRawFit=true`); на Oct 1–4 — по
   сглаженным 5-минутным бакетам. Это восстанавливается по записанной строке
   `Parabola fit results` и должно фиксироваться как вход цикла, а не угадываться.

Дополнительно закрылся вопрос инсулина: каждая запись болюса в Nightscout несёт `icfg`
(`Lyumjev 45m 8h 100 ед`, `insulinEndTime = 28 800 000`, `insulinPeakTime = 2 700 000`),
то есть DIA = 8 ч и пик = 45 мин — из самих данных, без перебора.

Где ещё остаётся разрыв, видно по цифрам выше:

- **Найден и исправлен look-ahead**: IOB-массив в приложении строится только по дозам,
  известным на момент цикла, а мост брал всю историю, включая будущие (в данных есть болюсы
  позже `now`, например утренний болюс 6.2 ЕД). Из-за этого предсказания падали до −700 мг/дл.
  После фильтра `timestamp <= now`: `rate` 192/250, `predBGs` p90 = 8 вместо 21.
- `rate` сравнивается с `suggested.rate`. `currentTemp` восстанавливается из собственной строки
  приложения (`"59m left and 0 ~ req 0U/hr"`, `"temp 0.675 ~< req 0.59U/hr"`), потому что
  `processedTbrEbData` в приложении восстанавливает *плановую* длительность temp, а запись в
  Nightscout содержит уже усечённую. После этого `rate` вырос с 52 до 69/120; оставшиеся
  расхождения — это `insulinReq` 0.53 против 0.59, то есть численная разница входов, а не
  другая ветка решения.
- Разложение по факторам autoISF на 250 циклах (модуль разницы): `pp_ISF` 0.000,
  `dura_ISF` 0.000 (p99 0.03), `bg_ISF` 0.000 (p99 0.01), `acce_ISF` 0.010 (p99 0.15), итоговый
  фактор 0.000 (p99 0.14). То есть `delta` (pp) и `duraISFminutes` воспроизводятся точно,
  `bgAcceleration` — с точностью до 0.01 на 90 % циклов; остаток даёт неполный сырой ряд CGM
  и состояние UKF (`learnedR`), а не другой коэффициент.
- `predBGs` расходятся на циклах с COB > 0: `slopeFromMaxDeviation` и `slopeFromMinDeviation`
  в Nightscout не пишутся, а без них COB-кривая строится неверно (вплоть до отрицательных
  `minPredBG`). Это следующий вход, который нужно восстанавливать — тем же
  `AutosensDataStore`, а не подстановкой констант. Пока W1 честно ограничен COB = 0.
- Остаточная ошибка IOB (~0.007 ЕД) и `delta`/`shortAvgDelta`/`longAvgDelta` — главный источник
  расхождения `rate` на нейтральных участках (наш 0.83 против нейтрального 0.75).

**Приёмка W1** (ревизия 2026-11-10, согласована после того, как выяснилось, какое состояние
рантайма не наблюдаемо ни в Nightscout, ни в базе xDrip):

Три уровня. Первый — обязательный, остальные два измеряют решения на уже проверенных входах.

**Tier 0 — входы (обязателен, иначе решения не о чём судить):**

| Вход | Порог | Факт (чистое окно) |
|---|---|---|
| `glucose` = записанный `bg` | ≥ 94 % точно | 237/250 (94.8 %) |
| `bgAcceleration` | p90 ≤ 0.01 | 0.005 |
| `IOB[0]` | p90 ≤ 0.02 ЕД | 0.013 |
| `mealCOB` | p90 ≤ 1.5 г | 0.0 |
| final ISF factor | p90 ≤ 0.02 | 0.01 |

**Tier A — решение:**

| Метрика | Порог | Факт |
|---|---|---|
| `smb` точно | ≥ 95 % | 96.8 % |
| `duration` точно | ≥ 90 % | 91.6 % |
| `rate` в пределах ±0.05 U/ч | ≥ 80 % | 82.4 % |

**Tier B — непрерывные выходы:**

| Метрика | Порог | Факт |
|---|---|---|
| `insulinReq` ≤ 0.01 ЕД | ≥ 80 % | 84.8 % |
| `insulinReq`, p90 | ≤ 0.05 | 0.03 |
| точки `predBGs` в пределах 5 мг/дл | ≥ 90 % | 92.3 % |

**Tier C — объяснимость:** 100 % расхождений `rate` попадают в один из классов таксономии
(нет изменения у приложения; обе стороны поставили разный temp из-за численной разницы входов;
look-ahead исправлен; `COB > 0` вне области W1).

Почему не 99 %: точное совпадение `rate` — пороговая функция от входов. Разница `insulinReq`
0.05 U/ч уже переключает ветку «ставить/не ставить temp». Входы, которые это решают
(плановая длительность temp basal из `processedTbrEbData`, состояние `learnedR` UKF), в
доступных выгрузках отсутствуют. При достигнутых tier 0 порогах 99 % по `rate` недостижимы
без AAPS-базы (root) — это и есть зафиксированный предел W1, а не ослабление критерия.

Сборка `a199b37` (Oct 15–22, с COB > 0) приводится в отчёте справочно и в приёмку W1 не
входит: там `smb` 79 %, `insulinReq ≤0.01` 68.5 %. Это отдельная задача (плановые temp basal).

Золотые данные сняты на 5-минутном каденсе, поэтому W1 проверяет только его. Каденс 1–4 мин
проверяется отдельно, без эталона: один и тот же 5-минутный ряд проигрывается на 1, 2, 3, 4 и
5 минутах, и сравнивается частота решений (SMB/сутки, коррекции в падающую глюкозу, доза).

## 8. Правила

- Ни одного физиологического числа без источника и страницы; иначе `TODO`.
- Не подбирать параметры под желаемый результат; допуски фиксируются до первого прогона.
- Детерминизм: одинаковые сиды — одинаковый результат, включая порядок суммирования IOB.
- **Персональные данные:** в devicestatus есть `_id`, `identifier`, `device`, `uploader`,
  `subject`, имя профиля, остаток резервуара. Вырезаются на импорте; в репозиторий и отчёты
  попадает только обезличенный jsonl. Проверять грепом перед каждым коммитом.
- Никаких клинических формулировок в отчётах.
