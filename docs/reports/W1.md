## 1. Что проверялось

Цель W1 — доказать, что JVM-мост воспроизводит решения настоящего приложения на его же данных.

- Target: `4.0-apex-integration` @ `74271a544b` (`4.0.0-74271a5-2026.10.06`).
- Данные: Nightscout, первый сайт; 11 780 уникальных циклов за октябрь 2026.
- Чистое окно: **2026-10-06 18:00 — 2026-10-07 19:04 UTC**, 250 циклов с `COB = 0`.
  Почему только оно — §2.
- Мост: `bridge/` (JVM), настоящие `UnscentedKalmanFilterPlugin`,
  `AutosensDataStoreObject`, `GlucoseStatusCalculatorAutoIsf`, `OpenAPSAutoISFPlugin.autoISF()`,
  `DetermineBasalAutoISF.determine_basal()`; IOB — `ICfg.iobCalcForTreatment` и `TB.iobCalc`.

## 2. Почему окно такое узкое

1. Сборка менялась почти ежедневно (12 версий за месяц). `74271a5` жил Oct 6–8 — 732 цикла.
2. Nightscout писали несколько приложений: Oct 1–4 параллельно `iGlucco` (≈1 мин), а
   Oct 7 19:04 UTC сменился xDrip-аплоадер (`Libre2` → `xDrip-LibreReceiver Libre2 Native`),
   поток стал ≈6-мин. После этого смены входной поток не совпадает с тем, что получал AAPS.
3. Внутри чистого окна приложение считало параболу по сырым 3-мин отсчётам
   (`useRawFit = true`), что восстанавливается по строке `Parabola fit results`.

## 3. Результаты

### 3.1 Входы

| Проверка | Результат |
|---|---|
| `glucose` после UKF+бакетирования vs записанный `bg` | 237/250 точно, p99 = 1.8 мг/дл |
| `bgAcceleration` vs `Parabola fit results` | медиана 0.003, p90 = 0.005, p99 = 1.84 |
| `corrSqu` | p90 = 0.000, p99 = 0.10 |
| `parabolaMinutes` | p90 = 0.0, p99 = 3.0 |
| `IOB[0]` vs `suggested.IOB` | медиана 0.007 ЕД, p90 = 0.013, p99 = 0.022 |
| `autoISF()` vs записанный `sens:` | 18/30 в пределах 0.1 |

Факторы autoISF по отдельности (250 циклов, модуль разницы): `pp_ISF` медиана 0.000 (p90 0.000),
`dura_ISF` медиана 0.000 (p90 0.000, p99 0.03), `bg_ISF` медиана 0.000 (p90 0.01, p99 0.01),
`acce_ISF` медиана 0.010 (p90 0.03, p99 0.15), итоговый фактор — медиана 0.000, p90 0.01, p99 0.14.
То есть `final ISF factor` совпадает с точностью до 1 % на 90 % циклов; отдельные «несовпадения»
`acce_ISF` — это разница в 0.01 на округлении до двух знаков, а не другой коэффициент.

Числа чуть ниже прежних 192/250 потому, что теперь `MealData` идёт из настоящего

Разбор расхождений `rate`: 16 циклов — приложение оставило текущий temp (`rate = null`), а мы
поставили новый; 4 — наоборот; 43 — обе стороны поставили temp, но значения разошлись

Найдена и исправлена отдельная ошибка моста: IOB-массив строился по всей истории доз, включая
болюсы с `timestamp > now` (в данных есть такие записи). Приложение их не знает, поэтому
предсказания уходили в −700 мг/дл. После фильтра `timestamp <= now` `rate` вырос с 69/120
до 187/250, а `predBGs` p90 — с 21 до 6.

### 3.4 База xDrip: точный поток CGM найден

В Nightscout после Oct 7 19:04 лежит не тот поток, что получал AAPS (2/80 точных `glucose`).
В экспорте базы xDrip (`BgReadings`) он есть: AAPS берёт `EXTRA_BG_ESTIMATE`/`EXTRA_RAW`, и
эмпирически воспроизводится колонкой **`raw_data`** (а не `calculated_value`).

`python/golden/export_xdrip.py <db> --column raw_data -o data/golden/cgm_db.jsonl` даёт
316 739 отсчётов; проверки на `a199b37` (Oct 15–22, 250 циклов):

То есть CGM-вход для поздних сборок закрыт.

### 3.5 COB/autosens-пайплайн подключён

`slopeFromMaxDeviation`/`slopeFromMinDeviation` и `mealCOB` нигде не сохраняются — их считает
oref1-пайплайн COB. В мост добавлена команда `meal`: она вызывает **настоящий**
`PrepareGraphDataRunner.runIobCobOref1` (через reflection, suspend-метод) на том же
`AutosensDataStore`, что и `glucose`, с настоящими `AutosensDataObject` и `IobCobCalculator`
(IOB считается теми же `ICfg.iobCalcForTreatment`/`TB.iobCalc`).

Проверка COB против записанного `suggested.COB` (10 циклов `a199b37`):

| записано | переиграно |
|---|---|
| 5.93 | 6.08 |
| 5.11 | 5.30 |
| 4.32 | 4.53 |
| 2.67 | 2.23 |
| 1.03 | 1.45 |

Расхождение 0.2–0.7 г — это разница сетки/момента, а не другая модель COB. Отдельно исправлена
дедупликация treatments: в Nightscout одни и те же болюсы и углеводы лежат по 2 раза, из-за чего
COB удваивался (7 716 → 6 361 запись).

Полный `step` на `a199b37` (200 циклов, уже с COB > 0):

| Метрика | Значение |
|---|---|
| `rate` | 126/200 (63 %) |
| `duration` | 184/200 (92 %) |
| `smb` | 158/200 (79 %) |
| `insulinReq` | медиана 0.00, p90 = 0.06, p99 = 0.29 |
| `eventualBG` | медиана 1, p90 = 20, p99 = 92 мг/дл |

Хвост `eventualBG` — это UAM-кривая (`UAMpredBG`), а не COB: на нескольких циклах с высоким BG

сходится (медиана 0.10, p90 0.40 мг/дл/5м), то есть slopes и углеводный вход посчитаны верно —
расходится форма кривой на будущих шагах (`iobWithZeroTemp`/predBGI), а не модель UAM.
Проверка «карб-запись создана позже цикла» не подтвердилась: в октябре нет ни одной записи
углеводов, созданной больше чем на 5 минут позже события.

## 4. Классификация расхождений

| Класс | Сколько | Причина |
|---|---|---|
| Приложение пишет `rate = null` | 16 | `currentTemp` в приложении — плановая длительность из `processedTbrEbData`, в Nightscout — усечённая. Восстановлено из строки `"Nm left and R ~ req"`; остаток — когда строки нет |
| Обе стороны поставили разный temp | 43 | Численная разница `insulinReq` (0.53 против 0.59 и т.п.) из-за IOB ±0.007 и `bgAcceleration` |
| COB = 0 у приложения, у нас > 0 | 1 цикл (55 г) | карб-запись есть в Nightscout, но на этот момент её нет в базе приложения |
| `acce_ISF` отличается на ≥0.01 | ~10/170 | Сырой ряд CGM неполный (несколько аплоадеров, смена источника); остаток — состояние UKF (`learnedR`) |
| COB > 0 | вне области W1 | slopes теперь считаются настоящим пайплайном; проверено отдельно на `a199b37` (§3.5, справочно) |

## 5. Что это значит

Мост честный: он вызывает настоящий код и воспроизводит сглаживание, параболу, IOB и `delta`
(pp_ISF 100 %). Но **приёмка W1 не достигнута**: 74.8 % `rate` при пороге 99 %. Остаток почти
целиком — численная разница входов на нейтральных участках: `rate` 0.98 против 1.15 при
`insulinReq` 0.07 против 0.05.

Следующие шаги по убыванию эффекта:

1. **`processedTbrEbData`.** Приложение восстанавливает плановую длительность temp basal, в
   Nightscout лежат усечённые записи. Это последний крупный вход, который влияет и на
   `currentTemp`, и на историю IOB → `slopeFrom…` → UAM. Проверено: реконструкция temp по
   цепочке *enacted* записей (сегмент «последний применённый temp живёт до конца своей
   длительности») даёт `rate` 88/250 — хуже, чем разбор `currentTemp` из строки `reason`
   (187/250). Значит enacted-записи в Nightscout не отражают то, что видел
   `processedTbrEbData`; нужен другой источник (AAPS не отдаёт базу без root, остаётся
   `TempBasalStart` + `TempBasalAbsoluteRate` из devicestatus).
2. **`currentTemp` для оставшихся циклов** без строки в `reason` — 16 расхождений `rate`.
3. **UAM-хвост.** `eventualBG` p99 86 мг/дл на циклах с высоким BG; COB при этом сходится
   (медиана 0), значит расхождение в slopes, а slopes — в истории IOB (см. п. 1).
4. **Сборки.** CGM закрыт базой xDrip (`raw_data`); проверены `74271a5`, `b2cce90`,
   `a199b37`; мост переносится между коммитами без правок.
